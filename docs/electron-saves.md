# Electron save pipeline

Gameplay saves use `saveRecordAsync`. The renderer captures a consistent snapshot, partitions it into zones, then a dedicated worker serializes and hashes changed zones. The worker sends at most 32 JSON blocks per batch and waits for the asynchronous Electron write acknowledgement before continuing. Electron skips existing content-addressed blocks and compresses new ones using asynchronous native gzip at level 1. Blocks use owner-independent zone-part-v2 payloads and numeric SHA-256-derived keys; the small root manifest still uses LZString. Legacy single-file and zone-part-v1 saves remain readable. The browser fallback still uses localStorage and its quota.

Each transaction stages exclusively created files. The root manifest is replaced by a temporary-file rename only after every block has been written. An index-publication failure restores the preceding root before discarding staged blocks. Shared blocks are collected only after successful publication, by tracing every indexed manifest. A missing or unreadable indexed save prevents collection. Deleting a root never directly removes shared blocks; they are reclaimed during a subsequent successful save once no indexed root references them. Closing a renderer aborts its staged transaction; a commit already underway completes. This protects against interrupted writes, but is not an fsync-based guarantee against sudden hardware power loss. A process crash before publication may leave unreferenced blocks on disk.

Compact resources cache immutable serialized snapshots by spatial zone. Explicit additions/removals dirty the affected zone; materialized handles and animated resources are inspected on each snapshot so direct gameplay mutations remain visible. Cold unchanged resources are not serialized again. Unchanged zone arrays bypass worker comparison during the session; persisted hashes also permit file reuse after restart. Moving entities and other mutable state are still captured each time. Snapshot flattening and ordering still visit entity references; this is not yet an entirely constant-cost incremental save.

Loading exposes reading, terrain/resources, visual preparation, save preparation, block progress and publication. The overall percentage is a weighted stage indicator, not a predicted remaining duration. It never decreases and reaches 100% only after boot and its initial save complete. A failed initial save leaves the ready world playable and displays an explicit warning that it has not been saved.

Restart Electron fully after updating main/preload. Compare `[save-zones]` (written/reused blocks) and `[save-timing]` (partition/native batch/publication/total milliseconds), first on a new 5k map and again after cutting a few trees. The first save in the shared format writes the whole state. Subsequent saves, including new manual slots and saves after restarting Electron, reuse existing matching blocks. Bulk compression now runs natively in Electron off the gameplay thread, but initial snapshot construction, partitioning and structured-clone transfer still run on the renderer and remain optimization opportunities.

## Resource differences relative to the blueprint

The active world's persistence snapshot now uses `resourceDelta` for a sealed `CompactResourceSet`. The baseline is sealed immediately after blueprint resources are generated, before village placement and gameplay. Its packed slot order and fingerprint identify the expected resource baseline. Baseline fields stay in the existing packed arrays; no second array of resource objects is constructed.

Deletes are recorded immediately. At snapshot time only materialized baseline handles are compared with their original state, so direct quantity/hit-point assignments remain supported. Cold untouched resources are never visited. Additions and dynamic/animated resources are captured with their current state, including wheat growth. The current implementation does not hook every direct property assignment; it still inspects materialized handles at save time. `[save-resources]` reports baseline, modified, removed and dynamic/added counts.

On load, the blueprint regenerates the baseline, whose count/fingerprint must match before applying changes. The loader reuses this packed collection, applies tombstones and overrides, rebuilds occupancy, and restores added/animated objects. An incompatible blueprint fails explicitly rather than silently applying changes to different resources. Old full-resource snapshots still load and are converted once against the generated baseline.

`serializeGame` remains the full simulation/travel snapshot API; `serializeGameForPersistence` is the active-world disk snapshot API. World transitions capture full outgoing states for the existing offline economy. If loading requires offline simulation, the loader temporarily expands the delta, runs the existing simulation, then derives the resulting changes. Thus inactive worlds captured for simulation can still contain full resource lists; the optimization currently targets the active packed blueprint world, including the 5k map. Editor/non-packed and other unsealed resource collections retain the full format. Terrain cells are not added to the save.
